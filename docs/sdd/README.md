## چرا و از کجا

این ساختار از ابزارهای زیر الهام گرفته شده و برای شرایط این پروژه ساده شده است:

| `speclib/awesome-openspec` | ایده‌ی archive و معیار پذیرش صریح در هر spec |
| `obra/superpowers` | برنامه‌ی کار ۵ دقیقه‌ای، test-first، تأیید قبل از اعلام پایان |

| `emotixco/claude-skills-founder` و `founder-playbook` | قالب اعتبارسنجی ایده/قیمت‌گذاری برای اسناد کسب‌وکار (نه کد محصول) |

> هیچ‌کدام از این مخزن‌ها کتابخانه‌ی زمان‌اجرا نیستند و وابستگی محصول نشدند. فقط روش و قالب وارد پروژه شد.

## ساختار

```text
docs/sdd/
  constitution.md        اصول غیرقابل‌مذاکره و دروازه‌های کیفیت
  001-everyday-ux/       نمونه‌ی کامل یک چرخه
    spec.md              سناریو، نیازمندی، معیار پذیرش، خارج از محدوده
    plan.md              تصمیم فنی، فایل‌ها، ریسک
    tasks.md             کارهای کوچک با مسیر فایل و روش تأیید
```

شماره‌گذاری: `NNN-نام-کوتاه`. spec تمام‌شده حذف نمی‌شود؛ بایگانی می‌شود تا تاریخ تصمیم بماند.

## چرخه‌ی هر تغییر

1. `spec.md` بنویس (سناریو + معیار پذیرش + اثر امنیتی/دسترسی‌پذیری).
2. `plan.md` (فایل‌ها، تصمیم، ریسک، «نمی‌سازیم»).
3. `tasks.md` را به کارهای ۵ دقیقه‌ای بشکن.
4. پیاده‌سازی + تست.
5. `npm run verify` و سپس بازبینی معیار پذیرش.
6. اگر معیار پذیرش تغییر کرد، spec را همان‌جا به‌روز کن — نه در توضیح شفاهی.
