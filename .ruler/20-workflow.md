# گردش‌کار توسعه (Spec → Plan → Tasks → Implement → Verify)

برگرفته از `github/spec-kit`، `speclib/awesome-openspec` و `obra/superpowers`؛ ساده‌شده برای این پروژه. جزئیات در `docs/sdd/README.md`.

## حلقه‌ی کار

1. **Explore** — قبل از نوشتن کد: کد موجود، `docs/sdd/`، و `README.md` را بخوان. اگر کتابخانه/API مطمئن نیستی، مستند رسمی همان نسخه را بخوان (قاعده‌ی Context7) — API از حافظه نساز.
2. **Spec** — رفتار مورد انتظار را در `docs/sdd/<شماره>-<نام>/spec.md` بنویس: سناریوهای کاربر، معیار پذیرش، حالت‌های خطا/خالی/بارگذاری، و اثر امنیتی/دسترسی‌پذیری.
3. **Plan** — در `plan.md`: فایل‌های درگیر، تصمیم‌های فنی، ریسک‌ها، و «چه چیزی را عمداً نمی‌سازیم».
4. **Tasks** — در `tasks.md` به کارهای ۵ دقیقه‌ای با مسیر فایل و روش تأیید بشکن. هر کار یک خط.
5. **Implement** — کوچک‌ترین تغییر کامل. بدون بازنویسی چیزهایی که درخواست نشده.
6. **Verify** — معیار پذیرش را اجرا کن (تست/typecheck/build). اگر شکست خورد، علت را درست کن، تست را تضعیف نکن.
7. **Archive** — وقتی spec کامل شد، در `docs/sdd/` بماند؛ تصمیم‌های بعدی به آن ارجاع می‌دهند.

## قاعده‌های اجرایی

- یک تغییر، یک هدف. اگر وسط کار کمبود نامرتبط دیدی: یادداشت کن در `tasks.md` بخش «بعداً»، نه اینکه بی‌صدا اضافه‌اش کنی.
- دیباگ سیستماتیک: بازتولید → کوچک‌کردن → ریشه‌ی علت → اصلاح → تأیید همان سناریو. حدس نزن.
- «تأیید قبل از اعلام پایان»: هر ادعا در گزارش نهایی باید به یک خروجی واقعی (خروجی تست، build، کد) وصل باشد.
- بعد از کامپکت‌شدن context یا شروع جلسه‌ی تازه، این فایل و `AGENTS.md` را دوباره بخوان.
